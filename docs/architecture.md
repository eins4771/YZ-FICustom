# 開発構成と通信仕様の方針

この文書は今後の実装方針です。APIやOTA機能が実装済みであることを示すものではありません。

```text
Flutterスマホアプリ ── HTTP / WebSocket ──┐
                                        ESP32 ECU
スマホのブラウザ ──── HTTP / WebSocket ──┘

Flutterスマホアプリ ── BLE/GATT ───────── ESP32 ECU（追加予定）
```

ESP32はWeb画面の静的ファイルも配信します。Flutter Webの成果物をESP32へ積む方式ではなく、小さいHTML/CSS/TypeScriptの成果物を使います。両クライアントで共通化するのは通信仕様、MAP形式、単位、バージョン番号、検証ルールです。

## 実装前に決定する項目

- ESP32の型番、Flash容量、PSRAMの有無、実ボードのピン割当。
- MAPの軸、サイズ、数値表現、単位、上限・下限、保存形式。
- データの項目数、ECU内部の収集周期、スマホへの表示周期、保存するログ量。
- Wi-FiのAP / STA構成、接続認証、クライアントの書込権限。
- 共通APIとMAP形式のバージョン、互換性判定、エラー形式。
- OTAスロットとWebファイル領域のFlash配分、署名・検証・復旧方式。

## MAPとファームウェアの更新

MAP更新は一時領域への受信、互換性・値の範囲・チェックサム検証、反映、不揮発保存を分けて設計します。RAMへの適用とFlashへの永続保存を区別します。

ファームウェア更新はESP32側のOTA機構で行います。スマホやブラウザからはビルド済みイメージを転送し、受信検証後に起動先を切り替えます。更新可否はECU側のエンジン状態・電源状態で判定する設計とし、切断・電源断・新イメージの起動失敗からの復旧を検証してから実機用途に進めます。

## データ取得と制御処理

制御処理、無線処理、画面表示、ログ保存は実行周期と優先度を分けて設計します。ログの時刻はECU側で付け、スマホへの表示周期と計測周期を分けます。初期段階は実機出力を動かさず、接続・読出しから段階的に実装します。
